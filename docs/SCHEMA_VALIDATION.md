# Validation du schéma StarMade

Vérification du 12 septembre 2026, à partir de `docs/database`, des seize classes de tables du jeu consultées uniquement en local, et du script HSQLDB de la fixture de tests. Les sources Java propriétaires sont exclues de Git et du paquet npm ; elles ne sont pas nécessaires aux tests. Leur consultation porte sur un extrait du jeu ; cette vérification ne vaut pas certification de toutes les versions de StarMade.

## Contrats vérifiés automatiquement

`tests/tables/schema-definitions.test.ts` compare les seize modèles à `tests/tables/schema-contract.json` : ensembles exacts des noms de colonnes et liste des colonnes `GENERATED BY DEFAULT AS IDENTITY`. Ce contrat contient uniquement les métadonnées du schéma de la fixture HSQLDB, vérifiées lors de l’audit, sans code source du jeu. Un contrôle impose que chaque modèle exporté dispose d’un contrat. Les tests sont autonomes et ne lisent aucune source Java privée.

`tests/tables/schema-arrays.test.ts` vérifie les tableaux SQL de `MINES.COMPOSITION`, `ENTITIES.LOCAL_POS` et `ENTITIES.DIM` : représentation JDBC `ARRAY[...]`, JSON, tableaux natifs et rejet des données non numériques. Les compositions doivent comporter six entiers signés de 16 bits. Les positions et dimensions ne peuvent contenir ni `NaN`, ni infini, ni nombres partiellement interprétés comme `12junk`.

`tests/tables/schema-binary.test.ts` vérifie :

- les 22 octets big-endian de chaque objet flottant, selon les écritures `writeShort`, `writeInt`, `writeFloat` de `SectorItemTable.getItemBinaryString()` ;
- les entrées vides et les deux formes d'encodage, objets métier et structures simples ;
- les 22 ordinaux de commandes partagés avec `starmade-decoder`, la taille de 1024 octets et la conservation d'un identifiant supérieur à `Number.MAX_SAFE_INTEGER` dans le binaire ;
- une capture indépendante JDK HashMap et le format Java ObjectOutputStream des télécommandes, ainsi que les entrées objet, Map et objet métier (y compris la conversion du format réseau) ;
- la conservation des identifiants 64 bits dans les données commerciales encodées.

## Défauts corrigés

| Défaut | Conséquence | Correction |
|---|---|---|
| `PLAYERS.ID` non déclaré auto-incrémenté | Validation d'un nouveau joueur sans ID refusée | Métadonnée d'identité alignée sur `PlayerTable.define()` |
| `MINES.ID` déclaré auto-incrémenté | Acceptation d'une mine sans identifiant pourtant exigé par le jeu | Retrait de l'identité artificielle ; validation d'ID obligatoire |
| Composition des mines limitée au JSON | Tableau JDBC `ARRAY[...]` interprété comme composition absente | Lecture des trois représentations et contrôle SMALLINT[6] |
| Parseurs de tableaux des entités trop permissifs | Objets JSON, chaînes numériques et nombres partiels acceptés | Vérification de tableaux de nombres finis |
| Documentation des commandes décalée après l'ordinal 3 | Référence incorrecte pour les commandes de flotte | Liste alignée sur le modèle et le décodeur ; limite des sources explicite |

## Corrections complémentaires issues des tests de branches

Les coordonnées des secteurs sont globales : `SectorTable.java` impose `secCoordIndex(X,Y,Z)` et recherche les secteurs sans `STELLAR`. Le modèle utilisait à tort `(X,Y,Z,STELLAR)` et des coordonnées relatives fictives. L'index, les conflits et la clé unique sont corrigés ; la clé descriptive avec système reste accessible par `getSystemContextCoordinateKey()`. La conversion vers une grille de 16 secteurs par axe, conformément au contrat du décodeur, prend en compte les coordonnées négatives. Une taille de grille explicite reste possible. Les coordonnées sont validées comme entiers signés de 32 bits.

Les noms `NPCFLT#...`/`GNPCFLT#...` étaient mal interprétés : le parseur de faction convertissait le groupe du préfixe en nombre et renvoyait `NaN`. Un nom absent était aussi classé NPC. Ces cas ont des tests dédiés. Le type de station chargé (`ENTITIES.TYPE = 1`) est maintenant distingué pour l'amarrage d'un membre de flotte. La réparation appartient à la catégorie principale OPERATIONS tout en fournissant du SUPPORT tactique ; le prédicat de support tient compte de cette appartenance partagée.

Les identifiants d'amarrage numériques égaux à zéro sont conservés au lieu d'être remplacés par le sentinel `-1`. Un ID de secteur nul ne devient plus artificiellement zéro. Les descriptions, classifications, relations optionnelles et formats binaires ont reçu des tests supplémentaires ; ils sont mesurés avec les tests existants dans c8.

Les branches rendues impossibles par leurs conditions précédentes ont été retirées : seconde vérification d'un amarrage `-1`, contrôle de positivité d'une capacité constante, recommandation de mine sans avertissement alors que l'inactivité produit toujours un avertissement, efficacité d'un membre à la fois indépendant et amarré. Les tests utilisent les états publics cohérents ; aucune exclusion de couverture n'a été ajoutée.

## Limites et points à distinguer

Les `DataType` des modèles sont des catégories applicatives : `INTEGER` couvre aussi `TINYINT`/`SMALLINT`, `VARCHAR` couvre `CHAR`, `BLOB` représente les `VARBINARY`, et `TEXT` représente actuellement les colonnes SQL ARRAY. Ces métadonnées ne décrivent donc pas avec exactitude un DDL à recréer ; conserver le schéma natif pour la création ou la migration d'une base.

La lecture tolérante des tableaux ne vérifie pas à elle seule leur écriture JDBC. Le Java du jeu utilise `PreparedStatement.setArray()` pour la composition des mines : une écriture complète doit conserver cette sémantique, et pas simplement stocker du JSON comme VARCHAR.

Les extraits initiaux n'incluaient pas `FleetCommandTypes`, `Fleet.serializeRemotes()` ni les définitions de toutes les permissions. Le contrôle complémentaire du 20 septembre ci-dessous confirme la sérialisation des télécommandes ; la validation indépendante de tous les ordinaux et permissions reste limitée. Les labels métier des slots de composition ne sont pas démontrés par `MinesTable.java`, qui traite ce champ comme un tableau opaque.

Les getters numériques historiques convertissent certains BIGINT en `number`. Les tests binaires conservent la précision avec `bigint`, mais cela ne garantit pas la précision de tous les getters SQL au-delà de 2^53−1. Une migration de l'API des identifiants demande un périmètre distinct et explicite.

Cette vérification ne couvre pas exhaustivement les requêtes de chaque contrôleur ni toutes les règles métier du jeu. La couverture globale lignes/branches est mesurée séparément par le rapport c8 ; aucun pourcentage global n'est déduit de cette revue du schéma.

## Exécution ciblée

```sh
node scripts/run-tests.mjs tests/tables/schema-definitions.test.ts tests/tables/schema-arrays.test.ts tests/tables/schema-binary.test.ts
```

Le lanceur exécute les tests depuis une copie temporaire de la fixture. Ces tests de contrats ne modifient pas la base du serveur de jeu.


## Mesure finale du périmètre modèles

Le passage ciblé du 12 septembre 2026 exécute **1 684 tests avec succès**. Les seize fichiers `src/tables/*/*Model.ts` atteignent chacun **100 % des lignes, branches et fonctions** : 13 709 lignes, 2 491 branches et 987 fonctions couvertes dans cette mesure. `BaseModel.ts`, les contrôleurs et les modules core sont mesurés dans le rapport global distinct ; ils ne sont pas inclus dans ces totaux.

La commande de diagnostic utilise la configuration de couverture complète, sans exclure les fichiers non exécutés ; son résumé global est donc volontairement inférieur au résultat de ce périmètre. Lire les entrées par fichier du JSON c8 pour contrôler le résultat des seize modèles. Les sources sont compilables avec `tsc --noEmit`.

```sh
node node_modules/c8/bin/c8.js --check-coverage=false \
  --reports-dir=/tmp/starmade-model-coverage \
  node scripts/run-tests.mjs 'tests/tables/**/*Model.test.ts' 'tests/tables/schema-*.test.ts'
```

Le drapeau `--check-coverage=false` sert exclusivement à cette exécution partielle de diagnostic. La validation globale conserve son seuil de 100 %.

## Compatibilité du décodeur — 20 septembre 2026

La dépendance locale `starmade-decoder` a évolué depuis la qualification du 12 septembre.
Les trois anciens échecs binaires ont été reproduits sur la révision antérieure au nettoyage
(`25c5ea9`), avec la même dépendance. La correction s'appuie sur les formats suivants :

| Cellule | Contrat et preuve |
| --- | --- |
| `FLEETS.COMMAND` | Une cellule absente/vide donne `null` ; une cellule non vide tronquée lève `DecodeError`. Le parseur strict du décodeur propage `E_FORMAT` pour ces sous-flux. Les tests conservent les assertions d'absence et ajoutent le rejet des longueurs 1, 8 et 12. |
| `FLEETS.SAVED_REMOTES` | `Fleet.serializeRemotes()` dans les sources locales New Foundations emploie Java ObjectOutputStream pour une HashMap. Tous les types d'entrée du modèle écrivent désormais ce format ; les lectures réseau restent acceptées. Une capture indépendante du JDK sert d'oracle et le JDK a relu la sortie du modèle. Les résultats de récupération incomplets sont refusés sans remplacer la valeur stockée. |
| `SYSTEMS.RESOURCES` | Le JAR installé et le schéma HSQLDB fourni utilisent 16 octets ; les sources locales StarMade-Open et le décodeur actuel exposent 19 emplacements. Les constantes du JAR ont été inspectées sans copier son code. Les cellules de 16 octets sont étendues de trois zéros uniquement pour la lecture. L'écriture reste à 16 octets par défaut ; passer explicitement `19` cible un schéma étendu. Toute perte de densités non nulles est refusée. |

La capture JDK conserve son seuil interne de redimensionnement HashMap. Pour comparer
l'écriture canonique du décodeur, le test attend ce champ à zéro ; ce champ ne contient
aucune télécommande et le flux ainsi produit a été accepté par ObjectInputStream.

Les fichiers de jeu restent des références locales privées. Aucun fichier Java ni JAR
n'est ajouté au dépôt ou au paquet. La fixture de 16 octets n'est ni migrée ni remplacée.
Les tailles non vides autres que 16 et 19 restent des erreurs de décodage ; les tests
vérifient la conservation des octets et les écritures sans perte dans les deux formats.
